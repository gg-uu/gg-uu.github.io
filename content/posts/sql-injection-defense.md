注入类漏洞长期位列 OWASP Top 10 前列。它本质上是一类「输入与代码边界混淆」的问题：当程序把用户可控的数据直接拼接到可解释的语句（SQL、命令、模板）中执行时，就产生了注入面。

## 漏洞成因

看一个典型的不安全写法：

```php
// 不安全：直接拼接用户输入
$query = "SELECT * FROM users WHERE username = '" . $_GET['username'] . "'";
$result = mysqli_query($conn, $query);
```

这里的核心问题：`username` 被当作字符串拼接进 SQL，而 SQL 引擎无法区分「数据」与「命令」，于是用户输入里的特殊字符就可能被当作 SQL 语法执行。

## 常见利用思路（理解原理即可）

注入的常规思考路径通常围绕：闭合原有语句 → 注释掉多余部分 → 探测数据库结构 → 提取数据。例如典型的报错注入：

```
# 通过单引号触发语法错误，观察数据库回显
username=admin' AND 1=1 -- 
```

> 注意：这里仅用于理解漏洞原理。在真实系统中，未经授权的注入测试属于违法行为，务必在授权范围内进行。

## 防御方案

防护的核心原则是**参数化与最小权限**：

```python
# 正确：使用参数化查询，数据与 SQL 分离
cursor.execute(
    "SELECT * FROM users WHERE username = %s",
    (username,)
)
```

1. **参数化查询 / 预编译语句**：从根上阻断拼接，是最有效的防御。
2. **输入校验与白名单**：对类型、长度、字符集做约束，但参数化之后这一步是纵深防御而非依赖。
3. **最小权限**：数据库账号只授予必要权限，限制利用后的影响范围。
4. **输出编码**：防止二次注入与存储型 XSS 联动。
5. **WAF 兜底**：Web 应用防火墙作为流量层兜底，但不替代编码层修复。

## 扩展：命令注入与模板注入

同样的「边界混淆」思想也出现在其他场景：

- **命令注入**：拼接字符串进系统命令，防御用参数化 API（如 `exec` 传数组而非字符串）。
- **模板注入（SSTI）**：用户输入进入模板引擎执行，防御用白名单与沙箱。

理解了「输入与命令的边界」这一抽象，所有注入类漏洞的防御逻辑就统一了：**永远不要让不可信数据进入可解释的上下文**。
